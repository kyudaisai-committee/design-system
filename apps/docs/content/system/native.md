Web・iOS・Androidで、操作の目的、用語、状態の意味を揃えます。たとえば「下書きを保存」と「申請を提出」は、どの端末でも別の操作として区別します。表示や画面の移動方法は、端末で慣れた操作に合わせます。

このページは各媒体に共通する設計指針です。現在の[コンポーネント一覧](/storybook/?path=/story/overview-component-catalog--browse)はWeb向けで、ネイティブアプリ用の部品は提供していません。

## 共通にするもの、端末に合わせるもの

| 共通にするもの | 端末に合わせるもの |
| --- | --- |
| 用語、状態名、操作する対象 | ボタンの配置、読み上げへの伝え方 |
| 背景・本文・主な操作・注意など、色の役割 | OSのシステム色、明暗、高コントラストへの対応 |
| 文字の階層、情報の優先順位 | 書体、文字拡大、操作領域、画面幅に応じた配置 |
| 入力・確認・受付結果の流れ | 画面遷移、戻る操作、日付・ファイルの選択 |

システムの無彩色の基調は、アプリでも共通に使います。年度ごとのテーマ色を、保存やエラーの意味に割り当てないでください。

## 戻る操作と、画面を閉じる操作を区別する

上の階層へ戻る操作と、短い確認画面を閉じる操作は目的が異なります。端末の戻る操作やジェスチャーを尊重し、操作前にいた場所へ自然に戻れるようにします。

入力中に戻る場合は、回答を保持します。破棄が必要なら、その前に確認してください。ログインやファイル選択から戻ったときも、元の対象と作業を引き継ぎます。

主要な移動先を並べるタブに、「提出」のような実行ボタンを混ぜません。大きな画面では側面のナビゲーション、小さい画面では下部のナビゲーションや開閉メニューなど、表示できる範囲に合わせて配置します。

## 文字と操作領域を、利用者の設定に合わせる

本文はOSの標準書体を基本とし、端末の文字サイズ設定に追従させます。文字が大きくなったときは、入力欄やボタンの高さも広げ、必要なら横並びを縦並びへ切り替えます。

標準のタップ領域は、iOSでは44×44pt以上、Androidでは48×48dp以上とします。小さなアイコンにも十分な押せる範囲と間隔を設けてください。pt・dpは端末の画面密度を考慮した単位で、Webのpxとは分けて扱います。

文字拡大や操作領域の考え方は、[Appleのアクセシビリティ指針](https://developer.apple.com/design/human-interface-guidelines/accessibility)と[Androidのアクセシビリティ指針](https://developer.android.com/guide/topics/ui/accessibility/apps)も参照してください。

## キーボードや画面端で、操作を隠さない

画面の切り欠き、システムバー、ジェスチャー領域を避けて情報を配置します。入力時にはキーボードが開くことを考慮し、入力欄、エラー、提出ボタンまで移動できるようにしてください。

スマートフォンの縦向きだけで確認せず、横向きやタブレットでも配置を確認します。比較表をそのまま縮小して文字を詰め込まず、列を保ったスクロールや、一件ずつの詳細表示を使います。

## OSの機能を使う前後も設計する

写真・ファイル選択、共有、認証、権限の確認には、そのOSの標準機能を使います。システム側では、開始前の目的説明と、取消・拒否・失敗からの戻り方を用意します。

カメラは読み取りを始めるときなど、必要になる場面で使用目的を説明します。通知を許可しない人も、システム内で案内を確認できるようにします。許可を取り消した後の状態も設計してください。

## 実際の端末で一連の操作を確認する

ブラウザーのプレビューに加えて、iOS・Androidそれぞれの端末で確認します。画面を開いた状態だけでなく、入力、確認、送信、結果表示までを操作してください。

- ライト・ダークの両方で、文字と操作が見分けられる。
- 最大の文字拡大でも、長い日本語やエラーが欠けない。
- VoiceOver・TalkBackによる読み上げで、項目名・状態・結果が伝わる。
- 戻る、閉じる、再ログイン、OSの許可拒否の後も、元の作業に戻れる。
- 通信が途切れても、入力内容と受付結果を取り違えない。

操作の意味や結果の伝え方は、[画面と操作](./patterns.md)と合わせて確認します。
