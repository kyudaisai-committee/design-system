---
title: 画面と操作
description: 入力から保存・提出・結果確認まで、システムに共通する画面のつくり方。
---

システムの画面では、何を操作しているか、今どの状態か、次に何ができるかを明確にします。たとえば申請画面なら、企画名と「審査中」の状態を示し、修正が必要なときは理由と再提出の操作を近くに置きます。

配色や文字、余白は[システムのデザイン](./DESIGN.md)を参照してください。

## 対象と主な操作を画面の上部に置く

画面の上部には、戻り先、ページタイトルと対象、状態・期限、主な操作を置きます。開催回、年度、団体、企画、利用中の立場を区別し、どの対象への操作かが分かるようにします。

年度や団体の切り替えでは、未保存の内容を保存するか破棄するか、利用者に確認します。切り替えた後に、元の対象への操作が残らないようにしてください。過年度の情報や編集できない情報には、その状態を添えます。

主要な移動先は、利用者の目的に合わせてまとめます。来場者には企画・地図・予約、参加団体には申請・連絡など、よく使う入口を優先します。管理用の操作は、権限のある利用者に表示します。

広い画面では[Sidebar](/storybook/?path=/docs/components-sidebar--docs)に移動先と現在地を示します。狭い画面では開閉するメニューに切り替え、移動先を選んだら閉じます。[画面全体の構成例](/storybook/?path=/story/patterns-applicationshell--default)で配置を確認できます。

## 一覧に戻ったときも、検索条件を保つ

検索、絞り込み、並び順、ページ番号は、再読み込みと戻る操作で復元します。詳細を確認して一覧へ戻るたびに、同じ条件を入力し直す必要がないようにします。Webでは共有してよい条件をURLに含められますが、個人情報や機密性の高い検索内容は含めません。

名称は折り返し、金額や件数は右揃えにします。ページの先頭・末尾でも前後のボタンの位置を保ち、移動できない側だけを無効にしてください。

「まだ申請がない」と「検索条件に合う申請がない」は、次にできることが異なります。前者は作成、後者は条件の変更・解除へ案内します。[審査一覧の構成例](/storybook/?path=/story/patterns-reviewlist--default)

## 保存・確認・提出を区別する

入力項目は、ラベル、補足、入力欄、エラーの順に置きます。ラベルは常に表示し、プレースホルダーで代用しません。必須項目には「必須」と記載し、文字数・単位・添付条件は入力前に伝えます。

メール、URL、確認コード、数値、日付、時刻には、それぞれの入力に合う部品を使います。確認コードは必要な桁数を下線で示し、貼り付けた数字やOSの自動入力を各桁に表示します。入力だけで勝手に送信しません。入力できる文字に制約がある場合も、日本語の変換途中で文字を消さず、確定後に条件と修正方法を伝えます。

| 入力内容                     | キーボードと補助機能                                                                                |
| ---------------------------- | --------------------------------------------------------------------------------------------------- |
| 名前・文章                   | 日本語を入力できる通常のキーボード。文章には複数行の入力欄を使う                                    |
| メールアドレス・URL          | それぞれに合うキーボード。先頭の大文字化と自動修正を無効にする                                      |
| 半角の英字・英数字           | 英字を入力しやすいキーボード。先頭の大文字化と自動修正を無効にし、使える記号を補足する              |
| 確認コード・数字だけの文字列 | 数字用のキーボード。先頭の0を保持し、確認コードは自動入力に対応する                                 |
| 数値                         | 非負の整数は数字用、小数は小数点を入力できるキーボード。負数を許すときは「−」も入力できる設定にする |
| 日付・時刻                   | 日付は`YYYY/MM/DD`、時刻は24時間表記。選択画面と入力欄で同じ値を示す                                |

キーボードの種類だけで入力値を制限せず、貼り付けや外付けキーボードからの入力も検証します。日付の選択画面では、日本語の年月・曜日と選択した日を示します。

繰り返し入力では、「1件目」などの見出しを入力ラベルより大きく太くします。ラベルは「名称」「数量」のように簡潔にし、読み上げには何件目の入力かを含めます。各項目の右上に×の削除ボタンを置き、表形式入力では行の末尾にゴミ箱のボタンを置きます。どちらも「項目2を削除」のように対象を含む読み上げ名を付け、他の項目の回答を保持します。

条件に応じて項目を隠す場合は、再表示したときの回答と、送信対象に含める条件をフォーム側で決めます。[入力部品の配置例](/storybook/?path=/story/patterns-formlayout--default)で、項目のまとまりとエラー表示を確認できます。

下書きの保存と正式な提出は、別の操作です。提出は「入力 → 内容の確認 → 提出 → 受付結果」の流れにし、確認画面から項目へ戻って修正できるようにします。戻った後も回答を保持してください。

保存状態は「未保存」「保存中」「保存済み」「保存できませんでした」で区別します。保存済みなら最終保存時刻を示します。提出完了は、サーバーで受理されたことを確認してから表示します。

### エラーは修正する場所と方法を示す

入力エラーは項目の近くに表示し、「100文字以内で入力してください」のように修正方法を書きます。提出時に複数のエラーがある場合は画面上部に一覧を置き、各項目へ移動できるリンクを付けます。折りたたまれた項目は開いてから移動します。

通信失敗や期限超過は、入力内容の間違いと分けて伝えます。日本語の変換中に入力を消したり、後から届いたデータで未保存の回答を上書きしたりしないでください。

手続きに必要な期限情報を取得できない場合は、画面全体をエラー表示に切り替えます。標準期限を代わりに示したり、進行表示の一部だけに「未確認」と置いたりせず、再読み込みなどの回復手段を用意してください。

ラベル・補足・エラーは読み上げでも入力欄と結び付くようにします。複数の選択肢には、設問全体の名前も付けます。[申請フォームの構成例](/storybook/?path=/story/patterns-applicationform--default)

## 添付ファイルは、選択した内容と送信結果を示す

選択したファイルの名前と容量を表示し、送信前に選び直したり取り消したりできるようにします。形式、件数、容量の条件は選択前に示してください。

送信を伴う画面では、送信中か、完了したか、再試行が必要かを伝えます。利用者の判断や操作に関係しない内部処理は、共通の状態として表示しません。ファイルの選択部品は、送信や保存の処理を利用側に委ねます。

## 状態には理由と次の行動を添える

| 状態                   | 表示と操作                                                                   |
| ---------------------- | ---------------------------------------------------------------------------- |
| 読み込み中             | 読み込んでいる対象を示す。まだ結果が届いていない状態を「0件」と表示しない    |
| データなし             | 対象がないことを説明し、作成など次の操作へ案内する                           |
| 処理中                 | 処理内容を文字で示し、同じ操作の連続実行を防ぐ                               |
| 完了                   | 対象・結果・時刻を残す。必要に応じて受付番号と控えを表示する                 |
| 失敗                   | 入力を保持し、原因と再試行の方法を伝える                                     |
| 結果不明               | 「受付状況を確認しています」と示す。結果を照会し、同じ操作を新たに送信しない |
| 権限不足・ログイン切れ | 再ログイン、利用先の切り替え、問い合わせなど可能な手段を示す                 |
| 期限超過・受付停止     | 対象の期限や停止理由を示す                                                   |
| 他の人による更新       | 最新の内容と手元の内容を確認し、必要な修正を選べるようにする                 |
| 通信断・古い表示       | 最終更新時刻と、最新の状態を確認できないことを伝える                         |
| 対象の削除             | 利用できない理由と戻り先を示す。別の対象へ自動で移動しない                   |
| カメラ・通知の許可拒否 | 必要な場面で理由を説明し、代わりの操作や設定方法へ案内する                   |

提出と審査、通知の受信と業務の完了は別の状態です。「提出済み」「審査中」は中立色、「要修正」は注意の色を使い、文字でも意味を示します。操作できるかどうかはサーバーの判定に従い、端末の時計やボタンの見た目だけで判断しません。

## 業務に応じて、確認する内容を選ぶ

| 場面                 | 画面に示す内容                                                                         |
| -------------------- | -------------------------------------------------------------------------------------- |
| 申請・審査           | 回答者、開催回、期限、提出版、審査状態、差し戻し理由。確定前に対象と判断内容を確認する |
| 予約・取消           | 日時、人数、場所、予約者、結果。取消前に期限や料金への影響を示す                       |
| QRコードの提示・受付 | 利用目的、対象、期限、読取結果。重複・失効・対象違い・通信断を区別する                 |
| 投票                 | 投票対象、選択内容、変更できるかどうか、受付結果。公開結果とは表示を分ける             |
| 支払案内             | 明細、支払先、方法、期限、入金確認の状態。入金記録と支払いの実行を区別する             |
| 連絡                 | 宛先、公開範囲、送信結果。送信・既読・返信・対応完了を同じ状態にしない                 |
| 地図                 | 場所の名称、凡例、更新時刻。地図以外からも対象を探せるようにする                       |
| AIによる補助         | 出力が提案であること、参照元、確認して採用する操作。正式な判断と区別する               |

権限、期限、料金、公開範囲などの業務条件は、各システムで定めます。共通部品は、その条件と結果を利用者に伝えるために使います。

QRを提示する画面には、[QRコードの3案](./qr-code.md)から用途に合う表示を選びます。対象と日時をコードの外にも書き、利用できないときはコード画像を取り除いて、理由と次の行動を伝えます。

## Webとアプリを移っても作業を続けられるようにする

Webとアプリで用語、状態名、操作結果を揃えます。移動するリンクには「Webで編集」など作業と移動先を示し、開催回・団体・対象・戻り先を引き継ぎます。戻った後は最新の状態を確認してください。

メールにも画面と同じ対象名・用語を使い、本文から次の操作へ進めるようにします。重要な案内は通知やメールだけに置かず、システム内でも確認できるようにします。

画面を確認するときは、入力から結果表示までを通して操作します。キーボード、読み上げ、文字拡大、狭い画面でも完了できるかに加え、通信失敗や再ログインから作業に戻れるかを確認してください。
